# Agent Note：Goal 的延续 Round 上限归部署所有

Status: implemented

[English](2026-09-13-deployment-owned-goal-round-cap.md) | 中文

## 问题

目标的停止条件在很大程度上由创建它的模型选定。`create_goal` 接受 `max_goal_rounds`，而 [`GoalService.create`](../../../../packages/goal/goal/README.zh.md) 只对自身未指定上限的创建请求应用 `defaultMaxGoalRounds`。因此，一个指定了 14 轮的模型会得到一个上限为 14 的目标，无论部署如何配置；而提高部署默认值毫无作用，因为模型自己的数字已经在请求里了。

[资源预算](2026-09-13-goal-resource-budgets.zh.md) 计量的是工作而非周期，但它们与 Round 上限是组合关系，而不是替代关系：`goal-round-driver` 先检查上限，再检查两个资源上限，因此模型指定的上限会在任何预算被查阅之前就停止续跑。预算还需要显式启用，未配置任何预算的部署观察到的行为与之前完全相同。只要模型还能指定一个更小的上限，部署就无法让自己的停止条件成为权威。

## 决策

`create_goal` 接受 `objective`，以及可选的这两个资源上限。它不再接受 `max_goal_rounds`，创建时也不向 `GoalService.create` 传递任何 Round 上限，因此每一个通过工具创建的目标都继承部署的 `defaultMaxGoalRounds`。

`update_goal` 在 `edit` action 上保留 `max_goal_rounds`。这现在是唯一会指定上限的工具路径，而 `edit` 本来就要求运行时根 agent 当前轮次中存在直接人类消息（[权限规则](2026-07-19-model-facing-goal-tools.zh.md)），因此上限只能由获授权的人类编辑或部署配置替换。

创建指引告诉模型：轮次数量与资源上限由部署决定，只有在人类要求时才指定预算。模型判断仍然决定一个请求是否算作目标；它不再决定该目标可以运行多久。

### 退役的参数是被移除，而不是获得默认值

参数声明不再包含该字段，而创建只读取它声明的字段，因此陈旧调用方仍会发送的参数对创建出的上限没有任何影响。发布的工具 schema 由同一份声明生成，因此该字段在同一次变更中从模型视野里消失；固定该 schema 的已录制快照 sidecar 也随之刷新。

## 测试

单元覆盖固定了两个方向：来自直接人类轮次的创建报告部署配置的上限；参数仍带 `max_goal_rounds: 9` 的创建报告同一个配置上限。无密钥录制会话通道通过随包发布的 headless profile 回放，其预期工具 schema 因参数对象变窄而重新录制。

## 后果

部署的 `defaultMaxGoalRounds` 现在约束模型创建的每一个目标，因此配置的默认值就是有效的停止条件，而由资源上限负责计量。基础 bundle 挂载目标包时不带任何配置，因此未作设置的部署保留该包自带的默认值。

该变更约束的是创建。已经记录在会话日志中的目标保留它存下的上限，人类通过 `update_goal` `edit` 或面向用户的命令路径来提高它。

Round 上限在领域中仍是 per-goal 字段，`GoalSnapshot.maxGoalRounds`、`GoalService.create`、`/goal` 命令和 Web 控件仍然指定它。只有面向模型的创建面变窄了。

## 考虑过的替代方案

**保留该参数，依靠指引让模型不要指定上限。** 否决：部署默认值只对省略该字段的请求生效，因此无视指引的模型仍会决定停止条件，而且没有任何东西会报告它这么做了。

**保留该参数，并把指定的上限向上钳制到部署默认值。** 否决：它保留了一个模型可见的旋钮，而其唯一可能的作用是缩短目标——正是部署要防止的结果；而且钳制会让报告的上限与模型发送的参数不一致。

**提高 `defaultMaxGoalRounds` 而不动工具面。** 否决作为完整修复：一旦模型指定了自己的上限，提高后的默认值就不再生效，而这正是产生所报告停止的条件。

**同时从 `update_goal` 移除 `max_goal_rounds`。** 否决：`edit` 是人类获授权通往该上限的路径，移除它会让日志中已记录的上限无法提高。
