# Agent Note: 插件市场面板可启用、停用与卸载已安装的插件

Status: implemented

[English](2026-09-11-marketplace-panel-write-controls.md) | 中文

## 问题

Web 插件市场面板只能读取状态，什么也改不了。用户看到某个插件列在那里之后想做的每一个动作——把它关掉、把它移除——都意味着离开浏览器、回到 `dsh plugin marketplace`，尽管同一个用户在同一台机器上早已认证了渲染该面板的同一个浏览器会话。第一版刻意不提供写入面，因为由浏览器发起的文件系统变更需要一套权限交代、一套确认交代，以及一套部分失败的交代，而状态读取不需要这些。

## 决策

面板管理的是**已经安装**的插件：启用、停用、卸载。安装、搜索与注册插件市场留在命令行，那里抓取、它钉住的 revision 及其进度都有地方报告。

**读取永不写入。** `marketplace.status` 从状态记录与插件自己的 `skills/` 目录解析拥有关系，并从 patch 层解析启用状态。它从不落地，因此打开一个设置标签页不会在磁盘上复制或移动任何东西。这正是早先只读界面要保护的性质，此处是保留它，而不是拿它交换。

**写入是否存在由部署决定。** gateway 的 `allowMutations` 组态栏位（预设 `true`）在写入路径本身检查，拒绝结果是一个 `marketplace/read-only` 失败，由面板渲染出来。面板会从状态快照读到同一个旗标，并在其为 false 时不绘制任何控件，但那只是显示输入：隐藏的按钮不是强制点，而共享同一个 harness home 的部署可以依赖这道检查，而不是依赖界面。

**每个操作只有一份实现。** 两个面调用的都是 `src/operations.ts` 的 `setPluginEnabled`，命令行的 `enable`／`disable` 现在也走它。每次写入还会返回它产生的那份状态，因此面板渲染的是写入之后的事实，而不是再发一次可能与刚完成的写入竞争的读取。

强制沿用了启用原本就有的两种机制：loader 行靠自身的 `disabled` 标志，skill 条目靠把它们在发现根目录与 `<root>/.disabled/<plugin>/` 之间移动。状态视图报告 patch 层答不出的东西——`skillIds`，以及取值为 `live`、`parked` 或 `none` 的 `skills`——因为 skill 靠发现挂载，没有任何行能描述它。

卸载被闸在显式勾选之后（`RiskConfirmation`，其确认按钮在勾选框被选中前一直不可用）；开关则没有。区别在于两者撤销的代价：停用把内容挪到一旁，启用把它们移回且无需重新抓取，而卸载会删除内容目录、已落地的 skill、行与记录。

面板不会绘制「唯一可能的结果就是被拒绝」的控件。什么都不挂载的插件没有开关，因为没有东西可移动；只读部署既没有开关也没有卸载按钮。某插件有写入在途时，它的确认按钮同样不可用。

接通写入路径时暴露出同一区域的一个清理 bug，位置就在[平铺的 skill 落地](../bug-fix/2026-09-11-marketplace-skills-land-flat.zh.md)刚改动的地方。原本一个函数既丢弃陈旧的条目名、又删除停放目录，于是 sync 第一次丢弃陈旧名称时，就把**已停用**插件唯一的 skill 副本一并带走了。两项职责现在分开：`removeMaterializedSkills` 只删除传给它的那些名称，而 `removePluginSkills` 是卸载用的更宽清理——那些名称，加上停放目录与更早布局所写的按插件隔离容器。

## 考虑过的替代方案

**也把安装与搜索放到面板上。** 延后而非否决。一次安装会解析来源、抓取它、钉住一个 revision 并报告该 pin；那需要一套单一请求与回应承载不了的进度与部分失败交代，而命令行已经在做了。卸载与启用都不需要这些工作，因此它们先行。

**只在面板里闸住写入。** 不予采纳。面板只是能触达同一 Remote 命名空间的其中一个客户端，而命令行可以在一次读取与一次点击之间改动某个插件。只在展示处强制的规则不叫强制。

**把 `allowMutations` 预设为 false。** 不予采纳。这个面板的操作者就是拥有该 harness home 的用户，浏览器会话已经通过认证，而这些操作每一个都只差一条命令行命令。预设关闭的面板是一个没人找得到的特性，而该栏位存在的意义恰恰是让想要只读姿态的部署能明说。

**连开关也要确认。** 不予采纳。启用可逆且不需要网络，确认只会训练用户随手关掉真正重要的那一个。风险在删除。

**让 gateway 拥有自己的一份启用逻辑。** 不予采纳。本包的历史就是一串「一个调用方重算了另一个已经解析出的东西」造成的失效，而「该插件拥有哪些行与条目」恰恰是这类派生事实。两个面可能同时开着，所以第二份副本维持不了多久就会不一致。

## 后果

- Remote 命名空间不再是只读的：`marketplace.setEnabled` 与 `marketplace.uninstall` 加入 `marketplace.status`，产生出来的客户端面同时携带这三者。
- 面板可以删除文件。这是该特性的代价，也是勾选确认闸门、逐卡片的拒绝信息与那个组态旗标存在的原因。
- `marketplace.status` 新增了三个必须保持诚实的栏位：`skillIds`、`skills` 与 `allowMutations`。
- `RemoteErrorDetailsMap` 新增 `marketplace/read-only` 与 `marketplace/not-installed`，因此拒绝会以稳定代码而非无类型失败抵达面板。
- 想要维持先前姿态的部署设置 `allowMutations: false`；面板届时会自我说明，而不是展示注定失败的控件。
- 卸载现在还会移除停放目录与更早的按插件隔离容器，因为记录一旦消失，就再没有任何东西能寻址那些路径。

## 测试

`tests/gateway.spec.ts` 覆盖写入面：skill 条目的停放与移回以及每次调用返回的状态、什么都不挂载的插件、卸载同时移除内容与 skill、只读拒绝，以及格式错误与未知插件的拒绝。`tests/skills.spec.ts` 钉住清理的分工，包括丢弃陈旧名称后仍保留已停用插件的停放副本。`tests/components.client.spec.tsx` 以受控夹具渲染面板：开关只出现在有东西可移动的地方、面板渲染的是主机端返回的状态而不是那次点击、卸载在勾选前不可用、拒绝落在它自己那张卡片上，以及只读部署完全不提供控件。
