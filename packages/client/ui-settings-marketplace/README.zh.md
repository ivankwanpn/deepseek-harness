# @deepseek-ai/dsh-client-ui-settings-marketplace

[English](README.md) | 中文

## 概述

在 Plugins 设置里使用 **插件市场** 标签页，查看插件市场安装了哪些插件、每个插件当前的状态，以及已注册的插件市场提供了什么。它会列出已注册的插件市场，并为每个已安装插件显示：钉住的 commit、能力、它拥有的加载器行与发现根目录条目，以及这些现在各自在哪；每张卡片带一个开关与一个 **卸载** 控件，后者因为会删除文件，必须显式勾选确认后才能执行。第三个区块按需读取可安装插件，在浏览器里过滤它们并从中安装一个；当主机端没有钉住该来源时，会先要求一次勾选确认。

<a id="use-this-package"></a>
## 使用本包

打开设置里的 Plugins 区块，选择 **插件市场** 标签页。在被选中之前它不读取任何内容；选中后才挂载组件，并通过 `api-remotes` 调用一次 `ctx.remote.marketplace.status()`。它下方的「可安装插件」区块在你索取之前同样不读取任何内容。

### 如何阅读一张卡片

每个已安装插件是一张卡片。标题是插件名，旁边的标签是它的状态：它拥有的每个加载器行都存在且开启时为 **已启用**；都存在且关闭时为 **已停用**；状态里有记录但补丁层没有对应行时为 **未挂载**；完全不拥有加载器行时为 **仅技能**。标签下方依次显示钉住的 commit、磁盘上检测到的能力、行 id 本身、它拥有的 skill 条目当前在哪（**已生效**、**已收起** 或 **无**），以及内容目录。事实列表下方的来源行标明该插件来自哪个插件市场。

**仅技能** 不是故障，因此也不按故障配色。只带 skills 能力的插件不挂载任何加载器行，因为 `skill-filesystem` 是从文件系统发现的；把它称作已停用等于告诉用户一个正在生效的插件是关闭的。它的 skill 位置回答了行状态答不出的那个问题。

### 打开或关掉一个插件

只要插件挂载了东西——加载器行、skill 条目，或两者——卡片上就有开关；什么都不挂载的插件没有开关，因为没有东西可移动。开关的位置就是插件的整体状态：它拥有的每种机制都开着时为开，任何一种关着时为关。

拨动开关会向主机端请求相反的状态，并渲染主机端返回的那份状态，因此控件跟随的是主机端而非那一次点击。写入进行中只会停用该插件的开关。这里没有任何确认：停用只是把 skill 与行挪到一旁而不删除，启用则把它们移回且无需重新抓取，所以两个方向都可逆。

### 卸载一个插件

**卸载** 会打开一个确认框，必须显式勾选后确认按钮才可用，标题里带有插件名。卸载会删除插件的内容目录、已落地的 skill、它的加载器行与安装记录，这些都无法恢复。

### 浏览并安装 catalog 中的插件

已安装清单下方的区块以一颗读取 catalog 的控件开启，它从已注册的插件市场读取；搜索框、结果列与重新整理控件在它应答之后才出现。这次读取是该标签页里唯一离开本机的读取，因此按需执行而不是在标签页打开时执行：一次 git 抓取不能拖住一个设置页。读取失败会在该区块内报告自己，并保留已经渲染出来的列；主机端读不动的某条注册会连同原因在那里被指名。

过滤发生在浏览器里，针对已经读回来的列，判定与命令行的 `search` 相同：对插件名、描述、category 与 tags 做一次不区分大小写的子字串测试，过滤词两端的空白会被去除，空过滤词匹配每一列。

一列显示插件名、已安装标记、描述、该条目自带的警告，以及当主机端的 pin 规则拒绝该来源时的警告标签。对主机端接受的列按下 **安装** 会一次调用完成安装；对主机端判为未钉住的列，它会打开一个确认框，其勾选声明写明缺失的 pin，且确认控件在勾选之前不可用。

安装之后面板渲染主机端回传的那份状态，并重新读取 catalog，因此已安装清单与该列显示的都是主机端自己对「现在装了什么」的看法。被拒绝的安装只会落在它被拒绝的那一列上，其他列不受影响。只读部署完全不绘制安装控件。

### 写入被拒绝时

被拒绝的写入会把主机端自己的信息渲染在它被拒绝的那张卡片上，其他卡片不受影响：一次拒绝不是页面级错误，面板也不会丢弃它已经拿到的状态。该信息携带主机端的拒绝码，这比一句还得猜是哪次拒绝的译文说得更多。

### 部署以只读方式提供面板时

部署可以关掉写入动词。状态快照会报告这一点，面板随即渲染一行简短说明而不渲染控件：开关、卸载按钮与安装控件都不出现，因此没有一次点击会失败。读取仍然工作，因为只读面板不等于不可用面板。

### 重试失败的读取

读取失败时显示一行简短失败信息与一个 **重试** 按钮。面板不显示传输层错误码，因为可采取行动的只有重试，而错误码不会改变用户接下来做什么。

<a id="understand-the-implementation"></a>
## 理解实现

### 设计理念

**它是请求面，不是权威。** 面板什么都不决定：它向主机端要一份状态、渲染那份回答，再要一次以改变其中一项。权限、归属规则与写入本身都住在 `packages/host/plugin-marketplace`，这也是关掉写入的部署会被遵守而不是被绕过的原因——那个旗标在写入发生的地方检查，而本包只是停止绘制控件。

**不会画的控件，就是不能动作的控件。** 在什么都不挂载的插件上放开关、在只读部署上放卸载或安装、在一次写入进行中允许再点一次：每一个都是「唯一可能的结果就是被拒绝」的按钮，因此面板干脆不画它。对那些面板看不到的情况（例如读取与点击之间有人在命令行做了改动），拒绝仍由主机端强制执行。

**不缓存任何东西。** 主机端每次调用都读取状态档并解析补丁层。两者都会在 harness 运行期间改变：命令行可以在浏览器开着的时候安装或停用某个插件，Cordis HMR 也可以随时重写补丁层。缓存的快照需要为每个写入方准备一条失效路径，而这次读取足够便宜，根本不需要。一次写入会返回它产生的那份状态，因此面板从不为了弄清自己做了什么而重新读取状态；它会在安装之后重新读取 catalog，以取得插件市场自己对「现在提供什么」的看法。

### 主机端读取的保证

主机端的 `status()` 从不落地。`materializeEntry` 会把 skills 复制进发现根目录，还可能把它们停放到 `.disabled` 下，因此以它为底的读取会因为打开一个设置标签页而顺带改动用户的磁盘。行 id 从每个已安装插件的 `.mcp.json` 推导，skill 归属则从状态记录或插件自己的 `skills/` 目录推导，因此这次读取能指名写入方会寻址的东西，而双方都没有写入。

catalog 读取同样什么都不写：它抓取每条注册的 manifest，并把它的条目映射成列，可安装性由主机端自己的 pin 规则判定。它的失败按注册逐条报告，因此一个读不动的插件市场无法让可读的那些所提供的结果变成空白。

启用状态只来自补丁层，与插件市场套件所声明的归属规则一致：存在性与来源在状态档，启用状态在补丁层。skill 是补丁层唯一描述不了的能力，因为它靠发现挂载；因此状态视图把它在哪作为一项独立事实携带，而不是从某一行反推。

<a id="model-experience"></a>
## 模型体验

### 插件市场面板

#### 模型看到什么

什么都没有。该面板是给人类操作者用的设置界面：它没有任何部分进入系统提示词、工具区块或消息流，模型也无法读取或调用它。面板所**报告**的内容——插件的安装路径、钉住的 commit 与行 id——描述的是别处挂载了什么，而任何真正到达模型的东西都是经由那些已挂载的行与被发现的 skills，而不是经由这个标签页：一个 MCP 行表现为 `mcp__<serverName>__<tool>` 形式的工具，一个被发现的 skill 则表现为一行目录，模型通过 `skill` 工具取得它。在这里使用的控件会在别处改变那些材料——停用一个插件会把它的行的 schema 移出工具区块并收起它的 skills，卸载则把两者一并移除——但那个改变属于被挂载的贡献本身，而本包不添加任何自己的文字。

#### Token 影响

自身为零。本包没有任何贡献被加入请求，面板自身的文字也只在人类打开该标签页时才渲染。一次写入会经由它改动的行或 skill，移动与等效命令行命令相同的 token 账目。

#### KV Cache 影响

自身为无。打开、读取或关闭面板都不会改变请求前缀中的任何内容，因此没有缓存边界会移动。面板发起的一次写入会移动其命令行等效命令所移动的那一个边界：行变化时是工具区块，条目进出发现时是 skill 目录。

<a id="known-limitations-and-deferred-work"></a>
## 已知限制与延期工作

- **写入本身没有进度。** 开关、卸载或安装会显示正在进行，然后显示结果，因为每一次都是一次请求；安装之后重新读取 catalog 才是刷新该区块的东西。
- **读取失败不做诊断。** 一次彻底失败的状态读取会渲染一个笼统的失败与重试，因为主机端的错误文本是文件系统或解析层面的诊断，需要操作者在终端里解决。catalog 读取是例外：读不动的注册会连同原因被指名，而已经读回的列留在屏幕上。
- **过滤判定存在于两处。** 面板在浏览器过滤，命令行在主机端过滤，因为两者是不同的程序；双方用同样的四个栏位钉住，因此分歧会是测试失败而不是无声的差异。
- **catalog 是一份快照。** 插件市场可能在读取与点击之间改变；主机端会在安装时重新解析该条目，因此记录的 pin 是当下的那个、而不是该列显示的。
- **未钉住的安装会记录一个你没看过的 commit。** 勾选确认许可这次安装；被记录的 revision 是该来源的 ref 在那一刻指名的那个。
- **注册插件市场不在这里。** 该标签页列出已有注册并从中安装；新增一个要用命令行上的 `dsh plugin marketplace add`。
- **没有更新或版本视图。** 面板显示钉住的 commit，但不显示插件市场现在是否列了更新的版本，因为本包没有任何东西会去解析上游 revision。

<a id="dev-note"></a>
### 开发备注

这里有两个决定是被建置逼出来的、不是选出来的，两者都记录下来，否则下一个人会再痛苦地发现一次：

- 主机端 `status()` 的返回类型会经由产生出来的 Remote 声明抵达**浏览器**编译面。早先的版本从 gateway 模组再导出线缆契约，这让前端建置去解析该模组，进而为一个浏览器目标编译整个 Node 侧套件——`node:fs`、`node:url` 全都在内。因此契约只住在 `types.ts`，而 gateway 只 import 它、不再导出。
- 同一个限制也移除了对 `@deepseek-ai/dsh-app-boot` 的 `PROFILE_PATCH_FILENAME` 的 import，因为那是 Node 专属的。改用字面值，并以注释指名真正拥有该常数的套件。
